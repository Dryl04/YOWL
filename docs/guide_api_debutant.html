1. Introduction générale

Ce guide t’explique pas à pas la partie API de ton projet Laravel. Tu es débutant : donc chaque mot technique sera défini clairement la première fois. L’objectif : que tu sois autonome pour lire, comprendre et étendre l’API.

2. Qu’est-ce qu’une API ? (Analogie du restaurant)

API veut dire « Application Programming Interface ». Imagine un restaurant : - Le client (ton application frontend, ou un utilisateur via Postman) demande un plat. - Le serveur (backend Laravel) reçoit la commande, la cuisine, et renvoie un plat. - L’API est le serveur + la carte qui explique “quels plats sont disponibles” et “comment les demander”.

Concrètement, une API web échange des données via le protocole HTTP (le même que ton navigateur). Les réponses sont souvent au format JSON (JavaScript Object Notation) : un format texte simple pour représenter des objets comme { "name": "Alice" }.

3. Aperçu rapide de Laravel (le framework)

Laravel est un framework PHP qui fournit des outils déjà prêts : - Routage (déclarer des URLs et ce qu’elles font) - Contrôleurs (organiser le code métier) - Eloquent (interagir avec la base de données via des objets) - Migrations (versionner la structure de la base) - Middleware (filtres entre l’entrée et la sortie, ex : authentification) - Sécurité (CSRF, hashing de mot de passe, validations)

Tu peux voir Laravel comme une boîte à outils organisée qui t’évite de « réinventer la roue ».

4. Anatomie d’une requête HTTP (Méthodes, URL, Corps, En-têtes)

Une requête HTTP est composée de : - Méthode : GET (lire), POST (créer), PUT/PATCH (mettre à jour), DELETE (supprimer). - URL : l’adresse, ex: /api/v1/posts. - En-têtes (Headers) : métadonnées comme Authorization: Bearer <token>. - Corps (Body) : données envoyées (souvent JSON) lors des POST/PUT.

Réponse HTTP : code de statut (200 OK, 404 Not Found, 401 Unauthorized) + corps JSON + parfois des en-têtes.

5. Structure du dossier api/ dans ce projet

Principales zones : - routes/api/v1/api.php : définition des endpoints. - app/Models/ : classes qui représentent les tables (User, Post, Commentaire, Relation). - app/Http/Controllers/Api/v1/ : logique qui répond aux routes (non listé ici mais utilisé dans les routes). - database/migrations/ : fichiers qui construisent/modifient les tables. - app/Notifications/ & app/Mail/ : envoi d’emails / notifications. - config/ : configuration (authentification, mail, sanctum, etc.).

6. Les Routes : la carte routière de l’application

Une Route associe une URL + une méthode HTTP à une action de contrôleur. Fichier : routes/api/v1/api.php.

Exemple :

Route::post('/login', [AuthController::class, 'login']);

Ici, quand le client envoie POST /api/v1/login, Laravel appelle la méthode login() de AuthController.

Le groupe Route::middleware('auth:sanctum') protège certaines routes : on exige un token valide (voir section 11).

Endpoints publics (extraits) : - GET /api/v1/ (Home) - POST /api/v1/register (inscription) - POST /api/v1/login (connexion) - POST /api/v1/password/reset (demande lien reset) - GET /api/v1/posts (liste des posts) - etc.

Endpoints protégés (exemples) : - GET /api/v1/me (profil actuel) - POST /api/v1/posts (créer un post) - GET /api/v1/post/{id}/like (aimer un post) - Gestion d’amis : POST /api/v1/friends/request …

7. Les Contrôleurs : les « chefs d’orchestre »

Un Contrôleur reçoit la requête, vérifie les données, appelle le modèle, et renvoie une réponse JSON. Il sépare la logique métier de la définition des routes. Même si les fichiers ne sont pas reproduits ici, ils suivent souvent ce schéma :

class PostController {
  public function getPosts() { /* récupérer tous les posts */ }
  public function createPost(Request $request) { /* valider puis enregistrer */ }
}

Analogie : le contrôleur est le chef d’orchestre, les modèles sont les musiciens, et la route est l’invitation au concert.

8. Les Modèles Eloquent : représentation des tables (objets vivants)

Un Modèle Eloquent est une classe PHP qui représente une table SQL. Exemple : User représente la table users.

Dans User.php : - $fillable liste les colonnes qu’on peut remplir en masse (sécurité contre injection). - $hidden masque des champs dans les réponses JSON (ex: password). - casts() convertit automatiquement les types (ex: dateOfBirth devient un objet Date).

Fonctions de relation (posts(), commentaires()) décrivent comment les tables sont liées (voir section 10).

Post.php inclut $fillable pour description, image, likes etc., et $casts pour convertir JSON -> tableau PHP.

Commentaire.php : chaque commentaire appartient à un utilisateur et un post.

Relation.php : gère amitiés (statuts : pending, accepted, rejected, blocked).

9. Les Migrations : l’historique de construction de la base de données

Une Migration est un fichier qui décrit comment créer ou modifier une table. C’est comme un journal de construction du bâtiment « base de données ».

Exemple (posts) :

Schema::create('posts', function (Blueprint $table) {
  $table->id();
  $table->text('description');
  $table->integer('likes')->default(0);
  // ...
});

Chaque migration a deux méthodes : - up() : appliquer (créer/modifier) - down() : annuler (supprimer/retirer)

10. Les Relations entre modèles (amis, posts, commentaires)

Types utilisés : - hasMany : un utilisateur a plusieurs posts. - belongsTo : un post appartient à un utilisateur. - belongsToMany : relation plusieurs-à-plusieurs (amis).

Analogie : - hasMany = un auteur → plusieurs livres. - belongsTo = un livre → un auteur. - belongsToMany = étudiants <-> cours (chacun plusieurs).

Dans User : - friends() + friendsOfMine() assemblent les amis dans les deux sens. - Méthodes utilitaires : isFriendWith(), sendFriendRequestTo() etc. encapsulent la logique.

11. Authentification avec Laravel Sanctum (jetons d’accès)

Authentification = prouver « qui je suis ». Laravel Sanctum fournit un système simple de tokens (chaîne de caractères secrète) envoyés dans l’en-tête Authorization: Bearer <token>.

Processus classique : 1. Tu POST /api/v1/login avec email + mot de passe. 2. Le serveur renvoie un token. 3. Tu l’utilises pour les routes protégées (ex: création de post).

Analogie : token = badge d’accès temporaire.

12. Activation de compte et réinitialisation de mot de passe

L’utilisateur a un champ is_active (boolean) et un activation_token. Lors de l’inscription on peut envoyer un email avec un lien /activate-account/{token} pour activer.

Réinitialisation : - POST /api/v1/password/reset = demander un lien. - POST /api/v1/password/reset/confirm = appliquer nouveau mot de passe avec le token reçu.

13. Gestion des Publications (Posts)

Modèle Post : colonnes principales - description : texte du post. - image, link : médias optionnels. - likes + likes_users (tableau JSON) : compteur + qui a aimé. - shares + shares_users : partages. - status : état (ex: publié, brouillon — dépend de ton usage).

Endpoints clés : - GET /api/v1/posts : liste. - POST /api/v1/posts : créer (auth requis). - GET /api/v1/post/{id} : lire un post. - PUT /api/v1/post/{id} : modifier. - DELETE /api/v1/post/{id} : supprimer. - GET /api/v1/post/{id}/like / unlike / share: interactions.

14. Gestion des Commentaires

Modèle Commentaire : - contenu : texte. - status : utile pour modération (ex: actif, masqué). Relations ajoutées par migration : post_id, user_id.

Endpoints : - POST /api/v1/posts/{postId}/comments : créer commentaire. - DELETE /api/v1/comments/{id} : supprimer.

15. Système d’Amitié et Blocage (Relations)

Table relations avec colonnes : - user_id (émetteur), friend_id (destinataire) - status : pending, accepted, rejected, blocked

Logique : - Envoyer demande : crée une ligne pending. - Accepter : passe à accepted. - Bloquer : passe à blocked + supprime toute autre amitié existante.

Endpoints : - POST /api/v1/friends/request - POST /api/v1/friends/accept/{friendshipId} - POST /api/v1/friends/reject/{friendshipId} - GET /api/v1/friends (liste acceptés) - GET /api/v1/friends/pending (en attente reçus) - GET /api/v1/friends/sending (demandes envoyées) - DELETE /api/v1/friends/{friendId} (retirer ami) - POST /api/v1/users/{userId}/block / DELETE /api/v1/users/{userId}/unblock

16. Rôles admin et endpoints réservés

Routes préfixées /api/v1/admin/* : - GET /admin/users - GET /admin/posts - Stats : GET /admin/stats

Ces routes supposent un rôle élevé (role dans users). Tu peux ajouter un middleware custom qui vérifie auth()->user()->role === 'ADM' par exemple.

17. Format des réponses JSON et bonnes pratiques

Bonnes pratiques : - Toujours renvoyer une structure cohérente :

{ "data": { ... }, "message": "Succès", "errors": null }
  • En cas d’erreur validation : HTTP 422 avec détails.
  • Éviter de renvoyer le mot de passe, tokens.
  • Utiliser codes HTTP adaptés (201 pour création, 404 si non trouvé, 401 si non authentifié).

18. Erreurs courantes et comment les éviter

Problème Cause Solution
401 Unauthorized Token manquant ou expiré Refaire login et inclure header Authorization
404 Not Found Mauvaise URL ou ID inexistant Vérifier endpoint / ID dans base
422 Unprocessable Entity Validation échouée Vérifier champs obligatoires
500 Internal Server Error Exception non gérée Lire logs storage/logs/laravel.log
419 Page Expired Token CSRF sur endpoints web Pour API, utiliser routes dans api.php

19. Comment tester les endpoints (exemples avec curl / Postman)

curl est un outil ligne de commande pour envoyer des requêtes. Exemples :

Connexion :

curl -X POST http://localhost:8000/api/v1/login \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"secret"}'

Supposons réponse : { "token": "ABC123" }.

Récupérer profil :

curl -H "Authorization: Bearer ABC123" http://localhost:8000/api/v1/me

Créer un post :

curl -X POST http://localhost:8000/api/v1/posts \
  -H "Authorization: Bearer ABC123" \
  -H "Content-Type: application/json" \
  -d '{"description":"Mon premier post"}'

21. Glossaire récapitulatif (tous les termes définis)

  • API : interface pour communiquer entre programmes (restaurant : serveur + carte).
  • JSON : format texte clé/valeur pour données.
  • Route : lien entre une URL et une fonction de contrôleur.
  • Contrôleur : classe qui traite la requête et renvoie une réponse.
  • Modèle (Eloquent) : objet représentant une table SQL.
  • Migration : script qui crée/modifie une table.
  • Middleware : couche intermédiaire filtrant la requête (ex: auth).
  • Token : chaîne secrète prouvant l’identité (badge).
  • Sanctum : système de gestion de tokens perso dans Laravel.
  • Relation (hasMany, belongsTo…) : lien logique entre tables.
  • CRUD : Create, Read, Update, Delete (opérations de base).
  • 422 : code HTTP pour erreur de validation.
  • 404 : code HTTP ressource absente.
  • 401 : code HTTP identité non prouvée.
  • Seeders : scripts pour remplir la base avec des données de départ (non détaillés ici mais présents dans database/seeders).
  • Factory : outil pour générer des objets de test.
  • Casting : conversion automatique de types (ex: date).

22. Prochaines pistes d’amélioration

  • Ajouter des tests automatisés pour chaque endpoint (Feature tests).
  • Ajouter validation (FormRequest) pour sécuriser input.
  • Documenter l’API avec Swagger/OpenAPI (déjà amorcé via annotations @OA).
  • Ajouter pagination (?page=1) sur liste de posts / users.
  • Limiter nombre de likes / interactions abusives (rate limiting).
  • Normaliser structure de réponse (créer une helper Response).
  • Ajouter rôle et permissions robustes (package spatie/laravel-permission).

Annexe : Problèmes Unicode lors de la conversion PDF

Si tu obtiens une erreur du type “Unicode character (U+2194) not set up for use with LaTeX” c’est que pdflatex ne gère pas directement certains symboles (flèches, émojis). Solutions : 1. Remplacer les symboles par ASCII (ex: ↔︎ devient <->, → devient ->, émoji ☕ devient (cafe)). 2. Utiliser xelatex ou lualatex avec pandoc qui gèrent Unicode :

pandoc guide_api_debutant.md -o guide_api_debutant.pdf --pdf-engine=xelatex
  1. Ou exporter en HTML puis imprimer en PDF via navigateur.

Script d’aide (créé séparément) utilisera un fallback.
